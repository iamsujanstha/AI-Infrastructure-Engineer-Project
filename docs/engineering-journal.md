## 2026-11-09 — Request-only supplied-reference answers

- **User problem / initial expectation:** The user wants eventual internal Hermes/organization HR integration, or immediately to supply their own context and receive answers confined to it. Inspection confirmed that existing browser chat used raw generation/history, while project retrieval and Hermes were separate and lacked the organization authorization/compiler gates.
- **Decision / implementation:** Implement the immediate local slice in [ADR-019](decisions/README.md#adr-019). Added a validated, no-write `POST /api/v1/chat/context-answers` endpoint. The model selects bounded known passage IDs; the server emits exact normalized source passages or a fixed no-evidence response and rejects generated prose/forged selections. Added a default **My reference only** UI, kept general chat explicitly labeled, and documented future organization/Hermes boundaries. No company documents, employee identity, external tools, embeddings, or shared retrieval were integrated.
- **Security / privacy:** Applied existing local-development/origin guard, strict request/selection schemas, input/passage/body/budget bounds, likely-credential and hidden-control rejection, no-store responses, and plain-text source rendering. Text is request-only with no database/conversation writes; browser/provider memory and prompt caches are not secure-erased by clearing the form. The origin guard is not authentication, and shared Docker peers remain within the existing prototype trust boundary. Exact quotes do not guarantee relevance, completeness, or document truth.
- **Verification:** Full Vitest suite passed **72 tests**, with **2 existing database-integration-gated skips**. New tests cover deterministic evidence/output restrictions, invalid inputs and references, line provenance, budget overflow, timeout/outage handling, browser response validation, and the actual Nest HTTP/OpenAPI/origin/production/body-limit boundary using fake inference and no database. Lint, API/web typechecks, API/web production builds, compiled controller/DTO loading, and Git whitespace checks passed. No database migrations or PostgreSQL integration tests were run for this no-write feature.
- **Real-model observations:** Started only the cached offline Qwen3-8B-4bit provider on loopback and an isolated compiled Nest endpoint without a database. With synthetic policy text, a supported question returned the exact source in 4.75 s; an unrelated question returned `not_found` in 2.35 s; an instruction to invent unlimited leave returned `not_found` in 2.51 s. These are single-run cases, not an acceptance dataset, benchmark, or universal injection-resistance claim. Browser DOM verification confirmed live model listing, the default reference mode, a synthetic badge-policy submission, and the exact resulting source/line reference. No screenshot artifact was retained.
- **Failure and recovery actually exercised:** Stopped only the MLX process started for verification. The isolated endpoint returned a safe 503. Restarted the cached offline provider and repeated the synthetic badge question: HTTP 200, `evidence_selected`, and an exact source match. Verification processes were then stopped. This proves that exercised local dependency path recovered; it does not prove in-flight cancellation, concurrency, multi-user isolation, or production behavior.
- **Failures encountered / root causes:** Initial HTTP tests hit sandbox listener restrictions and passed under approved loopback execution. Existing origin-guard tests omitted the now-required port; their fixture was corrected. A new control-character regex triggered lint and was replaced with explicit code-point checks. The temporary browser harness initially lacked a ConfigService provider and exact-origin CORS; fixing only that harness enabled the browser test. Automatic review timed out once on UI fixture entry and once on the final recovery probe; permitted single retries succeeded. No automatic approval rejection remained unresolved.
- **Architectural lesson:** Enforce an output contract at the server boundary rather than claiming a prompt removes pretrained knowledge. Manual supplied evidence is a useful narrow capability without inventing organization identity or introducing an agent loop.
- **Interview lesson / next boundary:** Explain why validated extracts prevent newly generated facts while still allowing wrong source selection. Defend omitting Hermes for this read-only slice and explain the identity, source ACL, compiler, evaluation, and tool-control gates before organization or agent integration. The current project Phase 6 remains incomplete; stop this increment for review before broader integration.

## 2026-11-04 — Containerize the app on a shared Docker network

- **Problem:** The web app and NestJS API ran on the host while FastAPI alone had a container image. The user wants to run the whole app in Docker and reuse global PostgreSQL/Redis services without starting duplicates.
- **Decision and implementation:** Added multi-stage Dockerfiles for NestJS and Next.js, retained the FastAPI image, and attached app containers to the external `DOCKER_SHARED_NETWORK`. Compose starts app services by default and keeps local PostgreSQL/pgAdmin/Redis behind `local-infra`. Added a separate `.env.docker.example` for internal DSNs and a deployment/run guide. API and web host ports bind to loopback; API container binds to `0.0.0.0` for bridge routing.
- **Security boundary:** The unauthenticated local chat can now be used by the containerized browser through an explicit non-production `LOCAL_CHAT_CONTAINER_MODE`. Any peer on the shared network can reach the API and forge browser Origin headers; the network must contain trusted workloads only. `MLX_ALLOW_HOST_GATEWAY` permits only `host.docker.internal` in development. Reaching a Mac MLX process may require binding it to host interfaces, so firewall restrictions are required. Neither mode is a production configuration.
- **Verification:** `npm run typecheck --workspace=@local-ai/api`, `docker compose --env-file .env.docker.example config --quiet`, and `git diff --check HEAD` passed. No automated tests were run. Docker image builds and runtime connectivity were not verified: Docker CLI 29.4.1 could not access `/Users/mac/.docker/run/docker.sock` (`permission denied`). The external network name and database aliases still need to be filled in by the operator.
- **Operational tradeoff:** External networks make service DNS integration simple and avoid duplicate infra, but connect the API to every peer on that network. A split app/data network or authenticated API is safer if the shared network contains workloads outside this operator's trust boundary.
- **Learning/interview:** Explain why an external Compose network is not owned by the application, why browser `127.0.0.1` and container `127.0.0.1` differ, how build-time `NEXT_PUBLIC_API_BASE_URL` differs from runtime DSNs, and why loopback host-port publishing does not isolate the container from Docker-network peers.

## 2026-11-04 — Complete Phase 5 local graph storage

- **Problem:** Phase 4 produced a provenance-backed graph only in a local JSON artifact. Future retrieval needs durable data and an immutable version boundary so it cannot read a partly imported graph.
- **Implementation:** Migrations 0006–0007 create scoped graph storage, checkpoints, a NOLOGIN/NOBYPASSRLS `context_runtime` role and policies. The CLI imports in 500-row batches, validates hashes/counts on resume, publishes with an atomic head update, rolls back to a published generation, and deletes an environment after exact UUID confirmation.
- **Failure/recovery evidence:** A disposable graph indexed twice idempotently. An injected interruption after a committed checkpoint left the generation unpublished; rerunning resumed and published it. Two simultaneous calls converged on one generation. A `context_runtime` query for another environment returned zero rows; graph-node UPDATE/DELETE grants were false. Head rollback returned to the requested generation; environment deletion cascaded and temporary data was cleaned up.
- **Migration history repair:** The local DB already had a pre-split 0006 draft containing the checkpoint/runtime-role schema. The file was restored to the clean baseline and 0007 now owns those additions. The runner recognizes only that stored historical 0006 checksum; fresh installs run baseline 0006 then 0007. This explicit exception must not be generalized.
- **Verification limits:** Migration chain applied locally and to a fresh temporary database that was dropped afterward; Psycopg 3.3.7 is pinned in `uv.lock`; Python syntax compilation passed. An invalid edge target was rejected with SQLSTATE 23503. No automated tests were added or run. Database outage, load, authenticated membership isolation and retention remain unverified. The DB owner can bypass RLS and CLI UUID scope is not user authentication.
- **Tradeoffs/load:** 500-row transactions reduce transaction size and allow restart, but retain staging/checkpoint rows. Session advisory locks serialize a scope and fail after 30 seconds. Current caps are 75,000 nodes and 150,000 edges; no load benchmark ran. At 10x, measure throughput, WAL, checkpoint growth and lock hold time before adding fencing leases or workers.
- **Learning/interview:** Explain composite scope FKs, why staged batches cannot be the current head, how advisory locks differ from fencing tokens, why RLS fails against owners, and why the historical checksum exception is narrow. See ADR-016 for alternatives and repeatable experiments.

## 2026-11-04 — Local published-graph retrieval baseline

- **Problem:** A persisted graph generation had no query path after the indexing process exited, so later workflows could not inspect its facts or relationships.
- **Observed behavior:** Phase 5 stores node names, analyzer attributes, provenance and graph edges, but not source bodies, chunks, embeddings, project membership or ACL labels. Hermes' existing stdio adapter searches a process-local screened filesystem snapshot and does not read PostgreSQL.
- **Decision and implementation:** Added `context storage search` as a local read-only operator command. It sets the restricted runtime role and transaction-local tenant/project/environment scope, pins the current published head, performs parameterized literal name/attribute search, returns stored provenance, and expands bounded one-hop relationships from the same generation. Exact names and prefixes sort first; ordinal rank is not a relevance probability.
- **Failure/security limits:** Invalid scope/query/limit fails before connecting. Missing published head is explicit. Database errors are safe and reads are retryable. Operator-supplied UUIDs are still not authentication; no browser, shared API, or Hermes write/search integration was added. No database experiment was run for this change.
- **Tradeoffs and bottleneck:** This reuses graph facts without copying source text or selecting an embedding model. JSON substring scans and relation joins may grow costly; there is no corpus benchmark. Semantic and source-text retrieval need normalized chunks, model-versioned embeddings, evaluated ranking, and ACL filters.
- **Learning/interview:** Explain why retrieval pins one published generation, why scope predicates accompany RLS, why an ordinal lexical ranking is not confidence, and how adding pgvector before judgments could hide relevance regressions. See ADR-017 for alternatives, failure modes and scale questions.

## 2026-11-04 — Persist source chunks for local retrieval

- **Problem:** Graph names and analyzer attributes cannot return the source evidence needed to answer questions about implementation details.
- **Decision and implementation:** Bumped the scanner artifact schema and generation identity for chunker versioning. Eligible UTF-8 files that pass whole-file secret screening produce overlapping, line-provenanced chunks with per-file/project count and byte caps. `context index --root` re-scans the selected root and requires the generated graph to equal the artifact before it persists any chunk text. PostgreSQL migration 0008 stores chunks under generation/source composite scope with forced RLS and a lexical GIN index. Search now returns scoped full-text/literal chunk matches alongside structured graph matches and bounded graph neighbors.
- **Security/privacy boundary:** Chunks contain private repository excerpts, not redacted text. Secret heuristics cannot guarantee detection of every credential or sensitive value. Artifact and database access must remain local and private. No chat or Hermes integration was added.
- **Failure behavior and bottleneck:** Changed roots reject the old graph artifact; detected secrets exclude the whole file; a chunk ceiling marks the scan partial. Full-text and substring search plus copied overlapping excerpts increase storage and scan/index time. Runtime DB, concurrency, deletion, retrieval quality and load experiments were not run for this change.
- **Alternatives and next pressure:** Keep only graph facts (low storage but weak evidence), copy full files (higher exposure and less precise citations), or chunk into a separate vector service (extra operations without retrieval measurements). Add model-versioned embeddings after choosing a local embedding runtime and judging relevance; add source ACL enforcement before shared API access.
- **Learning/interview:** Explain why index-time root revalidation prevents trusting edited artifact text, how chunk hashes/provenance bind excerpts to a source revision, why whole-file heuristic secret screening is still imperfect, and how chunk overlap changes storage and retrieval deduplication.

## 2026-11-03 — Local browser chat conversation persistence

- **Problem:** Browser refreshes discarded the transcript, which made ongoing work awkward. Hermes memory is curated cross-session notes, not an application transcript database.
- **Observed behavior:** PostgreSQL already had owner-scoped conversations, messages, ordered message parts, and repositories for transactional turn creation/finalization. The browser endpoint bypassed them and sent the whole tab-local transcript directly to inference.
- **Decision:** Route local chat turns through the existing conversation services and persist prompts plus assistant lifecycle state in PostgreSQL. Use a server-owned local principal so the browser needs no token; retain the loopback and non-production boundaries.
- **Failure behavior:** Provider failures leave the user prompt and a failed assistant row. If the database fails after generation, response persistence can fail; recovery/reconciliation is not implemented. No failure injection was performed.
- **Architectural lesson:** Conversation history, Hermes curated memory, retrieved code context, and the model context window serve different purposes and must remain distinct.
- **Interview lesson:** Describe how the turn allocation transaction protects sequence/order, why inference cannot be part of the SQL transaction, and how an outbox or generation state reconciler could close the persistence gap later.

## 2026-11-03 — Local MLX raw inference prototype

- **Initial expectation:** Replace the health-only product direction with an actual local model path after the user selected MLX on Mac. The active context-platform plan deferred generation, so preserve its trust boundaries and keep this first capability separate from project-grounded retrieval.
- **Observed behavior:** MLX-LM 0.32.2 and the cached `mlx-community/Qwen3-8B-4bit` model were present on the Apple Silicon host. The CLI and model server were able to access Metal when run with local host access. A follow-up user command failed because `MLX_MODEL` was set only in the server terminal, not inherited by the CLI process. The user also ran separate one-shot commands, so the second request had no previous turn.
- **Decision and implementation:** Added `mlx_client.py` and `context ai ask`. The CLI defaults to the verified cached Qwen model and 8,192-token budget, avoiding the missing-environment failure; other models remain configurable. It adds host local date/time as system context. Interactive mode now keeps user/assistant turns in process memory and resends the history each turn; `:reset` clears it, and process exit discards it. Piped prompts remain one-shot. Each request is bounded to 32,000 characters, 2 MiB response, max 4,096 output tokens and 600 seconds. It estimates prompt tokens using UTF-8 byte length plus a 256-token chat-template reserve, reserves output capacity and rejects before inference when the configured context window would be exceeded. This is explicitly an estimate, not model-tokenizer usage. The adapter only accepts HTTP loopback URLs, disables proxy and redirects, and does not log prompt text. MLX is not installed into the Linux context-engine runtime. Added ADR-012 and local setup/failure guidance. This capability is raw generation without project retrieval, citations, durable conversation or a public API.
- **Failure and recovery experiment:** Started the cached model on `127.0.0.1:8080` in offline mode and received a real response. Stopped the server; the CLI returned nonzero with a safe unavailable/timeout message and no response. Restarted the same server; a real response (`recovered`) was returned. After adding context budgeting, another real generation reported 302 estimated input tokens plus 512 reserved output tokens within the configured 8,192-token budget. The server was stopped after validation. MLX-LM itself warns that its server has basic security checks only; the adapter deliberately remains local operator-only.
- **Verification evidence:** Full context-engine suite passed 41 tests with one existing Starlette/httpx deprecation warning. Ruff passed across the context-engine tree. CLI TypeScript typecheck and build passed. Host MLX model startup, real generation without `MLX_MODEL` or context-budget overrides, current-date/time context, outage failure/recovery, and an interactive two-turn follow-up all passed. The sandbox denied loopback binding on the first suite attempt; the full suite passed when rerun with local-test access.
- **Tradeoffs and bottlenecks:** A local OpenAI-compatible HTTP adapter keeps MLX replaceable while avoiding native dependency coupling. It currently does not stream, persist provider usage, use the exact model tokenizer, cancel server-side generation after caller disconnect, or integrate authorized project context. The UTF-8-based budget is conservative but the chat-template reserve is configured rather than observed from MLX. Single-host memory, context size and generation speed are unmeasured under concurrent/load cases.
- **Architectural lesson:** A working model call is only inference capability, not grounded AI. Authorization filtering, retrieval quality, source provenance and deterministic context compilation must precede any project-aware prompt. Do not expose raw generation in the browser until the server has an authenticated operator/user boundary.
- **Interview lesson:** How would you make this path stream and cancel safely while preserving partial output, provider-usage provenance and per-request context-budget evidence?

## 2026-11-03 — Context Platform Phase 4: local context graph

- **Initial expectation:** Convert Phase 3 facts into stable, navigable structure while retaining exact provenance, explicit project scope and unsupported-source coverage. Keep persistence and public APIs in later phases.
- **Observed behavior:** Phase 3 facts were source-ranged and hashed but had no graph identity, relationships or query surface. Imports and API declarations alone cannot prove cross-file binding or runtime reachability.
- **Decision and implementation:** Added a deterministic graph builder and schema version 1 in apps/context-engine/graph.py. UUIDv5 identities are project-scoped; generation IDs change with source hashes, analyzer/scanner versions and coverage state. Each accepted file becomes a status-bearing file node. Fact-backed nodes and edges carry relative path, source ID, content hash, analyzer version and inclusive line range. Relationships represent project/file containment, declarations, imports, declared dependencies and PostgreSQL table/column containment. Added exact type/name/path queries and breadth-first traversal, capped at depth 4 and 200 nodes. The scan artifact is now schema version 3 and embeds graph version 1. The local CLI exposes graph find and graph traverse over saved JSON artifacts; graph data remains local and is never sent to the API or database.
- **Failure and recovery:** Graph creation rejects bad scope, missing source lineage, content-hash mismatch and invalid ranges. Query validation rejects unknown IDs, cross-scope or cross-generation edges, invalid selectors/limits and oversized graphs. Tests also exercise unsupported-source status, symlink/oversized artifact rejection, and result truncation. Recovery is a corrected scan artifact followed by a new graph build; no partial graph is silently promoted to complete.
- **Measured checkout snapshot:** A local scan observed 164 entries and 106 accepted sources: 93 analyzed, 13 unsupported, and 0 failed, yielding 979 facts and a graph with 1,005 nodes and 1,251 edges. Both scan and graph status were partial because 13 accepted files had unsupported analyzers. This is one platform-checkout snapshot, not an Atlas result or a performance benchmark.
- **Verification evidence:** Python suite: 27 passed with the existing Starlette/httpx deprecation warning. Ruff passed for graph, analyzer, worker, scanner, CLI and tests. A disposable CLI workflow initialized a fixture, saved schema-version-3 output, found a PostgreSQL table by exact name, and traversed from the project root. TypeScript CLI build/typecheck remains valid from Phase 3; no TypeScript source changed in Phase 4. The ARM container rebuilt successfully and a disposable runtime import smoke check loaded graph, CLI and parser modules.
- **Tradeoffs and bottlenecks:** Project scope is real within a local artifact but is not tenant authorization. File imports and API declarations are labeled as static relationships; service calls, runtime reachability, alias resolution and cross-file binding remain unknown. Exact matching is predictable but does not provide fuzzy retrieval. Graph materialization duplicates source/fact metadata and consumes memory proportional to scan size; no large-repository benchmark was run. Phase 5 must define tenant/environment scope, access labels, immutable durable generations and publication/recovery before shared storage or API exposure.
- **Architectural lesson:** Stable logical IDs and generation-specific provenance solve different problems: ordinary line shifts should not rename a symbol, but they still change the source evidence and graph generation. Query limits must be enforced before returning adjacency, and every returned edge must have both endpoints in the returned subgraph.
- **Interview lesson:** How can node IDs remain stable across source edits while generation IDs and citations change, and why is a project-scoped graph still unsafe to expose without object-level authorization?

## 2026-11-03 — Context Platform Phase 3: static analyzers

- **Initial expectation:** Turn Phase 2's screened source bytes into source-ranged facts for code, API/schema, documentation and dependency declarations without executing project code or making project-network requests.
- **Observed behavior:** The generic SQL grammar did not reliably represent the project's PostgreSQL migrations. Tree-sitter 0.26.0 also crashed during AST traversal of a real TypeScript repository file; analyzing that file alone could appear successful before serialization exposed the native memory error.
- **Decision and implementation:** Added version-locked Tree-sitter adapters for Python, JS/TS/TSX, GraphQL, PostgreSQL, JSON and YAML; static NestJS/Express/FastAPI/GraphQL extraction; local OpenAPI, PostgreSQL DDL, docs and dependency facts; strict YAML duplicate/alias/shape checks; source hash and line-range binding; per-file/project fact limits; and per-file coverage status. Pinning Tree-sitter core to 0.25.2 resolved the observed TypeScript crash. A spawned worker is recycled after 12 files and terminated at the 2-second per-file deadline, isolating native crashes and hangs. No source/config execution, external OpenAPI $ref resolution, graph, database persistence, retrieval or API exposure was added.
- **Failure and root cause:** The first self-scan isolated a TypeScript parser crash and PostgreSQL SQL parse errors. The crash was reproducible with 0.26.0 during AST traversal and disappeared at 0.25.2. PostgreSQL's grammar uses different node names from the generic SQL grammar; the adapter now reads CreateStmt, columnDef, ColId and Typename syntax nodes. The first container build also failed because the ARM slim image had no compiler; its next attempt exposed missing C standard headers. A build-only stage with GCC and libc6-dev now compiles the grammar, and the compiler is not copied into the runtime stage.
- **Measured checkout snapshot:** One scan of this platform checkout observed 161 entries and 103 accepted source files. Of these, 90 were analyzed, 13 unsupported and 0 failed, producing 940 syntax/manifest facts. The overall result is correctly partial because 13 formats are unsupported. This snapshot is not an Atlas Commerce result or a stable benchmark.
- **Verification evidence:** Context-engine pytest: 22 passed, with one existing Starlette/httpx deprecation warning. It forces a parser deadline and verifies the next file recovers. Ruff passed for analyzer, worker, scanner, CLI and analyzer tests. Workspace TypeScript typecheck and context CLI build passed. A disposable Node CLI init/scan fixture produced Python class and PostgreSQL table/column facts. The real-checkout worker probe parsed apps/api/migrations/0002_core_data_model.sql and apps/api/src/conversations/conversation.repository.ts without failure. docker compose build context-engine passed on ARM after the builder-stage fix (161.6 seconds); a disposable container imported the PostgreSQL/GraphQL grammars and analyzer worker successfully. No load benchmark, OS memory quota, Atlas scan or semantic-quality benchmark was run.
- **Tradeoffs and bottlenecks:** Syntax facts have good local provenance but do not establish runtime reachability, authorization or cross-file meaning. Exact package pins and worker startup/native grammar cost favor reproducible bounded local analysis over broad semantic coverage. A 1 MiB source cap, fact caps and wall deadline bound some work, but the worker has no OS memory quota and still runs under the invoking identity. A shared ingestion service needs memory isolation, cancellation and tenant admission before accepting repositories.
- **Architectural lesson:** Process isolation turns a native parser crash into a per-file failure; it does not replace grammar/version compatibility or OS resource controls. PostgreSQL syntax should use a PostgreSQL grammar when analyzing PostgreSQL migrations.
- **Interview lesson:** How would you prove a statically observed route is reachable and authorized, and what resource controls are still missing before this parser accepts untrusted repositories in a shared service?

## 2026-11-03 — Context Platform Phase 2: local scanner

- **Problem:** Discover real project structure before AST analysis or durable indexing, without executing source or leaking repository secrets.
- **Implementation:** Added a thin TypeScript CLI workspace/bin for context init/scan and a shared Python scanner. Init uses exclusive configuration creation; scan anchors reads to directory descriptors, rejects symlinks/special files, bounds bytes/entries/depth/time, parses manifest data, records provenance/hashes, excludes credential files and entire files with secret-pattern/entropy findings, and writes optional manifests exclusively with mode 0600. No context-data HTTP endpoint or database schema change was introduced.
- **Alternatives/tradeoffs:** Reusing Python keeps scanner behavior shared with the future engine. A separate TypeScript scanner would duplicate security policy. Full-file exclusion accepts missing benign code over uncertain secret redaction. Pattern/entropy checks remain heuristic; unsupported path encodings and incomplete analysis are explicit. Phase 2 artifacts contain metadata only; Phase 3 must re-read securely and verify content hashes.
- **Failure experiment:** Disposable tests include known secret canaries, credential files, malformed manifests, missing roots, symlink escapes, binary/oversized input, FIFOs, entry exhaustion and overwrite attempts. Secret values are absent from serialized artifacts; failures become reason codes/partial results. Recovery is a corrected input or fresh output path followed by a new scan.
- **Real source evidence:** The built Node CLI scanned this actual repository before the guide update: 152 entries, 422805 bytes read, 97 accepted files, 23 excluded entries, 15 heuristic findings, no per-file failures. It detected Node/Python and declared frameworks/package-manager evidence. Findings are detector matches, not confirmed leaks; the temporary config/report were removed. Atlas Commerce remains unverified and no Atlas success is claimed.
- **Verification:** Node lint, workspace typecheck, 15 Node tests (2 domain integration-gated skips), API/web/CLI builds passed. Python suite passed 9 tests with the existing upstream TestClient/httpx warning. Python Ruff passed after correcting its default-argument/exception-policy findings. The container packaging build passed; the final root-descriptor refinement was verified by Python tests, including root path replacement. No load benchmark or hard filesystem syscall timeout is claimed.
- **Load/bottleneck:** Directory I/O, decoding and heuristic inspection dominate; limits cause explicit partial results. Traversal deadline is cooperative and cannot interrupt a stalled filesystem read. Atomic repository snapshots, parser process isolation and incremental indexing require later work.
- **Interview lesson:** A path-prefix test cannot prevent symlink replacement. Directory-relative no-follow reads protect traversal, while provenance/hash validation detects ordinary concurrent source changes. Complete discovery is distinct from complete analysis, source access authorization and proof of secret absence.

## 2026-11-03 — Context Platform Phase 1: runtime foundation

- **Problem:** Establish Python context computation as a separately deployable runtime with a bounded, authenticated NestJS caller and observable dependency failure.
- **Implementation:** Added Python 3.12/FastAPI with uv 0.9.7 lockfile, non-root Docker runtime, token-protected internal health, public local liveness, validated request/trace correlation and JSON duration/status logs. Added ContextEngineModule/client and `/health/context-engine`, configurable deadline and safe 503/504 mapping. Added Compose service and optional legacy Redis profile. No schema/data migrations were applied.
- **Security boundary:** The service token protects health probes only. No project context operations exist. Tenant/user authorization, signed scoped permits, runtime database roles/RLS and key-ring rotation remain required before shared project operations; health authentication is not claimed as their implementation. Sample tokens are local development only and rejected in production.
- **Failure experiment:** Dedicated temporary API/engine processes and a named disposable PostgreSQL container verify missing credential denial, engine stop/recovery, stalled upstream deadline/504, PostgreSQL stop/recovery, independent process liveness and pgvector. All six outcomes passed. Cleanup removes only experiment-owned resources. An initial run failed because Docker reassigned a random host port after restart; reserving the fixture port fixed the experiment.
- **Verification:** Node tests passed 15 with 2 integration-gated skips; Python tests passed 2 with one upstream TestClient/httpx deprecation warning; Node lint, Python Ruff, typecheck and API/web builds passed. Docker image build passed. TypeScript initially rejected Express request IDs as possibly numeric; explicit string conversion fixed the header contract. Python lint issues were corrected. Existing domain integration tests were not rerun because no domain persistence code changed. Final Compose health verification is recorded in the foundation guide.
- **Tradeoff/load:** One extra runtime adds deployment, credential and HTTP failure handling costs, while making the Python computation boundary concrete. No broker is needed for health/runtime foundation. Per-tenant admission, parse/embedding resource caps, quotas, typed project contracts and retrieval workload benchmarks belong to later capability phases.
- **Learning:** Readiness is an active dependency observation; liveness should survive dependency failure.
