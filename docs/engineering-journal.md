# Engineering Journal

## 2026-11-03 — Context Platform Phase 2: local scanner

- **Problem:** Discover real project structure before AST analysis or durable indexing, without executing source or leaking repository secrets.
- **Implementation:** Added a thin TypeScript CLI workspace/bin for context init/scan and a shared Python scanner. Init uses exclusive configuration creation; scan anchors reads to directory descriptors, rejects symlinks/special files, bounds bytes/entries/depth/time, parses manifest data, records provenance/hashes, excludes credential files and entire files with secret-pattern/entropy findings, and writes optional manifests exclusively with mode 0600. No context-data HTTP endpoint or database schema change was introduced.
- **Alternatives/tradeoffs:** Reusing Python keeps scanner behavior shared with the future engine. A separate TypeScript scanner would duplicate security policy. Full-file exclusion accepts missing benign code over uncertain secret redaction. Pattern/entropy checks remain heuristic; unsupported path encodings and incomplete analysis are explicit. Phase 2 artifacts contain metadata only; Phase 3 must re-read securely and verify content hashes.
- **Failure experiment:** Disposable tests include known secret canaries, credential files, malformed manifests, missing roots, symlink escapes, binary/oversized input, FIFOs, entry exhaustion and overwrite attempts. Secret values are absent from serialized artifacts; failures become reason codes/partial results. Recovery is a corrected input or fresh output path followed by a new scan.
- **Real source evidence:** The built Node CLI scanned this actual repository before the guide update: 152 entries, 422805 bytes read, 97 accepted files, 23 excluded entries, 15 heuristic findings, no per-file failures. It detected Node/Python and declared frameworks/package-manager evidence. Findings are detector matches, not confirmed leaks; the temporary config/report were removed. Atlas Commerce remains unverified and no Atlas success is claimed.
- **Verification:** Node lint, workspace typecheck, 15 Node tests (2 domain integration-gated skips), API/web/CLI builds passed. Python suite passed 9 tests with the existing upstream TestClient/httpx warning. Python Ruff passed after correcting its default-argument/exception-policy findings. The container packaging build passed; the final root-descriptor refinement was verified by Python tests, including root path replacement. No load benchmark or hard filesystem syscall timeout is claimed.
- **Load/bottleneck:** Directory I/O, decoding and heuristic inspection dominate; limits cause explicit partial results. Traversal deadline is cooperative and cannot interrupt a stalled filesystem read. Atomic repository snapshots, parser process isolation and incremental indexing require later work.
- **Interview lesson:** A path-prefix test cannot prevent symlink replacement. Directory-relative no-follow reads protect traversal, while provenance/hash validation detects ordinary concurrent source changes. Complete discovery is distinct from complete analysis, source access authorization and proof of secret absence.

## 2026-11-03 — Context Platform Phase 1: runtime foundation

- **Problem:** Establish Python context computation as a separately deployable runtime with a bounded, authenticated NestJS caller and observable dependency failure.
- **Implementation:** Added Python 3.12/FastAPI with uv 0.9.7 lockfile, non-root Docker runtime, token-protected internal health, public local liveness, validated request/trace correlation and JSON duration/status logs. Added ContextEngineModule/client and `/health/context-engine`, configurable deadline and safe 503/504 mapping. Added Compose service and optional legacy Redis profile. No schema/data migrations were applied.
- **Security boundary:** The service token protects health probes only. No project context operations exist. Tenant/user authorization, signed scoped permits, runtime database roles/RLS and key-ring rotation remain required before shared project operations; health authentication is not claimed as their implementation. Sample tokens are local development only and rejected in production.
- **Failure experiment:** Dedicated temporary API/engine processes and a named disposable PostgreSQL container verify missing credential denial, engine stop/recovery, stalled upstream deadline/504, PostgreSQL stop/recovery, independent process liveness and pgvector. All six outcomes passed. Cleanup removes only experiment-owned resources. An initial run failed because Docker reassigned a random host port after restart; reserving the fixture port fixed the experiment.
- **Verification:** Node tests passed 15 with 2 integration-gated skips; Python tests passed 2 with one upstream TestClient/httpx deprecation warning; Node lint, Python Ruff, typecheck and API/web builds passed. Docker image build passed. TypeScript initially rejected Express request IDs as possibly numeric; explicit string conversion fixed the header contract. Python lint issues were corrected. Existing domain integration tests were not rerun because no domain persistence code changed. Final Compose health verification is recorded in the foundation guide.
- **Tradeoff/load:** One extra runtime adds deployment, credential and HTTP failure handling costs, while making the Python computation boundary concrete. No broker is needed for health/runtime foundation. Per-tenant admission, parse/embedding resource caps, quotas, typed project contracts and retrieval workload benchmarks belong to later capability phases.
- **Learning:** Readiness is an active dependency observation; liveness should survive dependency failure. A total deadline must include response consumption, and a health service credential grants no permission to retrieve project data. Interview question: how can an API remain operational enough to report an upstream outage while failing dependent operations safely?

## 2026-11-02 — Phase 1: local foundation

- **Problem:** Provide a runnable control plane and API with dependency health, startup configuration, request correlation, and local PostgreSQL/Redis services.
- **What I initially thought:** The system could defer ORM and migrations until the data-model phase while using a low-level pool for the first health probe.
- **What actually happens:** The initial brief named Prisma, so the first foundation used Prisma 7 and a Prisma migration baseline. After reviewing the tradeoffs, the project owner chose direct `pg` access to keep SQL, pool behavior, and transactions visible for the stated learning goals.
- **Implementation:** Added Next.js/React/Tailwind web control surface, NestJS API, Zod startup validation, Pino structured logs, request IDs, safe exception mapping, API versioning, CORS/body/rate limits, PostgreSQL readiness through a shared `pg.Pool`, Redis readiness through a lazy client, graceful resource shutdown, Compose dependencies, and a checked-in SQL migration runner. Replaced Prisma in application code and dependencies before domain tables existed; retained the old local migration metadata table rather than deleting database state.
- **Failure encountered:** TypeScript exposed an intersection type error when normalizing the CORS origins setting; changed the environment type to omit and replace the parsed field. Turbopack attempted a process/port operation blocked by the sandbox; selecting Next's Webpack build path produced a successful build without weakening the app's runtime permissions. The first live route probe also showed that version-neutral controllers still inherited Nest's global prefix; explicit health-route exclusions corrected the paths. A first pass through the exception filter hid safe `not_configured` health metadata; readiness now returns a classified response and is logged as a warning.
- **Root cause / fix:** The CORS parser's input and output representations differ (`string` to `string[]`), so an intersection retained the incompatible string member. The build failure was environmental rather than a CSS/application error. Nest's global prefix is independent of route version neutrality, so operational paths needed explicit exclusions.
- **Verification evidence:** The original Prisma migration installed pgvector. The replacement `pg` runner then independently recorded and reapplied the extension migration without dropping data. Live checks returned 200 for liveness, PostgreSQL, Redis, and `/api/v1`; inference returned 503 with `not_configured` as expected. Lint, typecheck, 11 unit tests, and both production builds passed. API/web development servers bind to loopback by default because authentication is not part of this phase.
- **Architectural lesson:** Separate operational probes from domain schema design. A checked-in migration can establish an extension prerequisite now, while Phase 2 can still design domain tables from explicit access patterns. Verify framework route behavior through HTTP, not just the controller metadata or application logs. A custom migration runner is operational code with concurrency, integrity, and recovery obligations; raw SQL alone does not remove those responsibilities.
- **Interview lesson:** Explain why liveness should remain healthy during a dependency outage, why a local in-memory limiter does not enforce a global quota, how to hold one pool client for a transaction, and how an advisory lock plus checksums make migration deploys safer.

## 2026-11-02 — Phase 2: PostgreSQL data model

- **Problem:** Design durable storage for ownership-scoped projects, conversations, messages, agent runs, memory, documents, model profiles, inference usage, context snapshots, jobs, and audit records.
- **Constraints:** Keep the schema relational and inspectable through raw SQL; preserve ownership constraints in the database; support pgvector without guessing a future embedding model; build no application repositories or domain workflows before their later phases.
- **Decision:** Use UUID primary keys, composite owner-scoped foreign keys, per-conversation message sequences, checked statuses/token counts, explicit soft deletion on mutable records, full-text GIN indexes, and scope/order B-tree indexes. Store vectors with per-row dimensions and defer ANN indexing until retrieval quality and workload are measurable.
- **Implementation:** Added migrations `0002_core_data_model.sql` and `0003_scope_active_uniqueness.sql`, plus data-model, index, transaction, and scaling guides. The follow-up migration separates project-scoped from user-scoped document dedupe because PostgreSQL treats NULL values as distinct in ordinary unique indexes.
- **Failure encountered / fix:** None during migration execution. The review identified that a single unique index including nullable `project_id` would not deduplicate user-level documents, and that a fully unique model-instance key would prevent reusing a key after soft deletion. Added targeted partial indexes and exercised those cases in an integration test.
- **Verification evidence:** Raw migration runner applied migrations 0002 and 0003 to PostgreSQL 17 with pgvector. The database integration test passed against that instance, covering all 20 core tables, case-insensitive email uniqueness, cross-owner project rejection, vector dimension validation, user-scope document deduplication, chat context limits, and reuse of a retired instance key. Lint, typecheck, 11 unit tests, and the integration test passed; final build is recorded after the docs update.
- **Architectural lesson:** Relational integrity can encode tenant scope and lifecycle invariants, but it cannot replace authorization checks or state-transition policy. Indexes are executable workload assumptions, and nullable scope keys require explicit uniqueness semantics.
- **Interview lesson:** Explain why a composite foreign key can prevent cross-tenant references, how NULL affects uniqueness, when to defer vector indexing, and how to benchmark an index without assuming the planner must use it.

## 2026-11-02 — Phase 3: conversation persistence

- **Problem:** Add durable conversation lifecycle operations without sending full stored history to a model or exposing owner-scoped data through unauthenticated routes.
- **Constraints:** The identity, token-budget, model-router, and provider-streaming phases are not implemented. Keep ownership predicates in persistence queries, keep provider I/O outside transactions, and persist partial assistant output without allowing concurrent generations to corrupt message order.
- **Decision:** Export internal application services and repositories from the Nest conversation module; do not add HTTP controllers until trusted authentication context exists. Allocate message positions while locking the conversation row. Persist user input plus an assistant placeholder atomically; append assistant text into a stable message part; finalize once into complete/failed/cancelled. Store retry/regeneration lineage and branch snapshots explicitly.
- **Implementation:** Added `0004_conversation_lifecycle.sql` for source-message/generation lineage and `0005_conversation_state_guards.sql` for source requirements and a partial unique index that enforces one active assistant response per conversation. Added owner-scoped `ConversationService`/`MessageService`, repositories, transactional turn creation, partial output/finalization, retry/regeneration, archive/rename, pagination, and branch copying with parts. Updated lifecycle, transaction, schema, migration, and local-development documentation.
- **Failure encountered / fix:** The initial `tsx watch` launch left constructor dependencies undefined because the dev transpilation path did not provide Nest's emitted constructor type metadata. Added explicit `@Inject(...)` tokens on constructor dependencies and explicit config-module exports/imports; the API then started normally. Review also found that returning an empty message-part ID would violate the persistence contract, so the repository reads the inserted part back inside the transaction. A service-only stream check would not protect future SQL write paths, so migration `0005` adds a database uniqueness guard.
- **Verification evidence:** Migrations `0004` and `0005` were applied to local PostgreSQL 17 with pgvector. `npm run test:integration` passed both database integration files; the conversation test exercises cross-owner invisibility, ordered turn creation, partial text appends, concurrent-stream rejection, completion, retry after failure/cancellation, regeneration lineage, branch copying, rename/archive, and archived-write rejection. `npm test` passed 11 tests with 2 integration-gated tests skipped; lint, typecheck, and both API/web production builds passed before the final explicit-injection startup fix. After that fix, `npm run dev` started both servers, web/API/PostgreSQL/Redis readiness probes returned HTTP 200/healthy, and lint and typecheck passed again.
- **Architectural lesson:** A service method can orchestrate lifecycle policy, but storage constraints remain the last line of defense. Locks serialize one conversation's writers; short database transactions must end before provider calls or user-facing streaming.
- **Interview lesson:** Explain why a partial unique index encodes one active generation, why retries create a new assistant record, how branch copies preserve ownership-safe message lineage, and why a disconnected client still needs a durable cancellation outcome.

## 2026-11-02 — Product direction reset and real-status repair

- **Problem:** Reorient the product as an AI Systems Laboratory and ensure the existing System health view reflects actual dependencies instead of a browser-origin failure.
- **Observed state:** The home page was a single health view with a static Phase 1 badge and milestone copy. The API, PostgreSQL, and Redis were healthy under direct probes, but the browser showed all dependencies offline. The UI had no engineering workflow navigation; most schema-backed capabilities still lacked services/APIs.
- **Decision:** Keep the existing health capability and backend foundations. Document the product direction and staged information architecture, require real backend capability before each lab view, and fix the current local-origin mismatch before changing the UI.
- **Implementation:** Added the current architecture/UI assessment, capability gaps, information architecture, and phased migration plan in `docs/architecture/ai-systems-laboratory-plan.md`; made the real-data, backend-first, and failure-experiment rules part of `AGENTS.md`. Aligned the local API URL and CORS defaults for IPv4 loopback while retaining the localhost origin.
- **Failure encountered / fix:** The UI called `http://localhost:4000` from `http://127.0.0.1:3000`, but the default CORS allowlist only permitted `http://localhost:3000`. An origin-header probe confirmed the API omitted `Access-Control-Allow-Origin` for the page origin while accepting the localhost origin. The page therefore reported “API unreachable” for a CORS failure even though the API was healthy. Updated the API client and allowlist; the refreshed page now reports API, PostgreSQL, and Redis online and inference as not configured.
- **Verification evidence:** `npm test` passed 12 tests with 2 integration-gated skips; lint and typecheck passed; the production build passed. The first parallel typecheck/build attempt hit a transient missing `.next/types` race; rerunning typecheck after the build completed passed. Live browser checks showed API/PostgreSQL/Redis `online` and inference `not configured`; direct API readiness probes returned 200. The screenshot was captured inline during this audit; no local screenshot artifact was produced.
- **Architectural lesson:** A reachable health endpoint is not enough if the browser cannot read it. Cross-origin configuration is part of the observed system path, and a client-side catch-all “offline” label can hide the true failure class.
- **Interview lesson:** Explain how to distinguish dependency failure from browser transport/CORS failure, why `localhost` and `127.0.0.1` are different web origins, and why UI state should preserve the failure class rather than imply the service itself is down.
